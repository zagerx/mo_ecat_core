# mo_ecat_core 配置系统统一方案

## 1. 背景

当前项目处于从“硬编码示例”向“可配置产品”过渡的阶段。主站启动选项、机器人拓扑等仍分散在 C 代码和未解析的 YAML 模板中。本方案的目标是把**产品/应用层可变配置收敛到 YAML 文件**，通过**宿主机代码生成器**在构建期转换为 C 数据，目标程序运行时不解析 YAML。

具体约束与契约详见《配置系统设计原则.md》；本文档描述总体架构、实施阶段和迁移路径。

## 2. 当前配置现状

| 配置类别 | 当前载体 | 使用者 | 状态 |
|---|---|---|---|
| 主站启动配置 | `struct mo_ecat_master_config` | 核心库内部 `master_init()` → SOEM `ecx_init` | 仅含 `interface_name`，编译进核心库 |
| 机器人应用配置 | `struct robot_config` | CLI → `robot_build()` | 默认配置是 C 硬编码数组；`examples/cli/config/robot.yaml` 仅作模板，未解析 |
| 后端专有选项 | 宏，如 `MO_ECAT_SOEM_IOMAP_SIZE` | SOEM 后端 | 改大小需改代码重编 |

## 3. 当前做法的缺点

1. **改配置必须改代码重编**：网口、机器人关节等写在 C 代码里。
2. **配置分散**：机器人拓扑与扫描结果缺少统一来源。
3. **状态机缺少配置阶段**：扫描完成后 PDO 映射、DC 检查、总线激活未被触发。
4. **后端参数固化**：IOmap 大小等通过宏固定。

## 4. 设计目标

1. 产品/应用层可变配置收敛到 YAML。
2. 构建期代码生成，目标程序零 YAML 运行时依赖。
3. 核心库与应用层解耦。
4. 允许在创建期、`DISCOVER`、`CONFIGURING` 一次性分配资源；`RUNNING` 禁止动态分配、文件 I/O、YAML 逻辑和阻塞打印。
5. 硬编码默认配置仅作为示例/测试 fallback。

## 5. 核心架构

### 5.1 配置分层

```
YAML 文件
  └─ 宿主机代码生成器 (mo_ecat_config_gen)
        ├─ struct mo_ecat_master_config     → 核心库内建主站参数（仅 interface）
		└─ struct robot_config              → CLI 机器人拓扑

运行时
  └─ 主站主动扫描总线
        ├─ 读取每个从站默认 PDO 映射
        ├─ 检查所有从站 DC 能力
        └─ 建立 IOmap 和过程映像
```

- 核心库消费内建的 `mo_ecat_master_config` 和扫描结果，不依赖 YAML。
- 后端类型和参数由 CMake/宏固定，不通过 YAML 配置。
- 机器人应用消费 `robot_config`，并在运行时与主站扫描结果比对。

### 5.2 文件划分

| 文件 | 职责 | 归属 |
|---|---|---|
| `src/config/master.yaml` | 只包含主站网口名 `interface` | 核心库主站配置 |
| `examples/cli/config/robot.yaml` | 机器人名称、关节、功能组、从站身份 | CLI 机器人配置 |

### 5.3 代码生成器

- 工具名：`mo_ecat_config_gen`，目录 `tools/config_gen/`。
- 使用宿主机 `libyaml` 解析 YAML。
- CMake 构建期自动调用，输出到 `build/generated/`。
- 生成器输入输出契约、版本规则、校验规则、错误格式详见《配置系统设计原则.md》第 5 章。

### 5.4 `mo_ecat_master_config`

```c
struct mo_ecat_master_config {
    char interface_name[MO_ECAT_MAX_IFNAME_LEN + 1];
};
```

## 6. 状态机与时序（概要）

稳定状态：`INIT`、`IDLE`、`READY`、`RUNNING`、`FAULT`。
内部过渡状态：`SCANNING`、`CONFIGURING`、`ACTIVATING`。

```
INIT → IDLE → CONFIGURING → READY → ACTIVATING → RUNNING
           ↑_________↓   ↓_________↓          ↓________↓
           └───────────────────────────────────────────┘
                              FAULT
```

- `DISCOVER` 只能从 `IDLE` 发起；失败进入 `FAULT`。
- `CONFIGURE` 只能在 `IDLE` 中扫描完成后发起；失败进入 `FAULT`。
- `ACTIVATE` 只能从 `READY` 发起；失败进入 `FAULT`。
- `FAULT` 后必须先 `RESET` 回到 `IDLE`，再重新 `DISCOVER` 和 `CONFIGURE`。

完整命令表、失败行为、**命令提交与异步执行结果的区分**、资源释放责任详见《配置系统设计原则.md》第 7 章。

## 7. PDO、DC 与过程映像（概要）

- PDO 映射由主站在 `CONFIGURING` 阶段读取各从站默认 PDO 映射获得，不从 YAML 加载。
- 系统总是尝试启用 DC；**所有**已发现从站（包括非机器人从站）必须支持 DC。
- IOmap 大小、SDO 超时等由后端宏或 CMake 选项定义。
- 应用层通过公开 API 查询从站信息、PDO 引用和过程映像只读视图；具体接口、**数据复制策略**、代际失效规则、**过程映像视图的并发有效性**详见《配置系统设计原则.md》第 8 章。

## 8. 实施阶段

### 阶段 1：简化主站配置模型

1. `mo_ecat_master_config` 只保留 `interface_name`，并由核心库内部持有。
2. 删除 `mo_ecat_user_config`、`mo_ecat_slave_config`、`mo_ecat_pdo_entry_config`。
3. 更新后端 `configure()` 签名，直接使用扫描结果完成 PDO 映射和 DC 检查。

### 阶段 2：扩展状态机

1. 新增 `CONFIGURING`、`READY` 等状态，新增 `CONFIGURE` 命令。
2. `CONFIGURING` 阶段执行：读取默认 PDO、检查 DC、建立 IOmap。
3. 机器人模块在 `IDLE` 中扫描完成后调用 `robot_build()` 校验身份。

### 阶段 3：实现代码生成器

1. 创建 `tools/config_gen/`，使用 `libyaml`。
2. 读取 `src/config/master.yaml` 生成核心库内建的 `g_master_config`。
3. 读取 `robot.yaml` 生成 `g_robot_config`。
4. 校验规则遵循《配置系统设计原则.md》第 5 章。

### 阶段 4：CMake 集成

本机构建：

```cmake
add_executable(mo_ecat_config_gen tools/config_gen/main.c ...)
target_link_libraries(mo_ecat_config_gen yaml)

add_custom_command(
    OUTPUT ...
    COMMAND $<TARGET_FILE:mo_ecat_config_gen> ...
    DEPENDS mo_ecat_config_gen ...
)
```

交叉编译/嵌入式需采用预编译宿主机工具、独立宿主机构建或预生成 C 文件三种策略之一，详见《配置系统设计原则.md》第 6 章。

### 阶段 5：改造 CLI

```bash
ecat_cli
```

- 配置在构建期固化；CLI 不读取主站配置，主站由核心库内部使用 `g_master_config`。
- 不接受运行时 YAML 路径和网口覆盖。

### 阶段 6：后端参数 CMake/宏化

- `MO_ECAT_SOEM_IOMAP_SIZE` 等通过 CMake 选项或宏定义。
- YAML 中不出现后端参数。

### 阶段 7：Fallback 与迁移

- 保留 `robot_default_config()` 等默认配置，仅用于示例/测试。
- 产品构建必须启用代码生成；生成失败阻止构建。
- 示例/测试 fallback 通过独立 CMake 选项或独立 target 启用。

## 10. 生成产物示例

### 10.1 `mo_ecat_master_cfg.h`

```c
#ifndef MO_ECAT_MASTER_CFG_H
#define MO_ECAT_MASTER_CFG_H

#include "config/master_config.h"

extern const struct mo_ecat_master_config g_master_config;

#endif
```

### 10.2 `mo_ecat_master_cfg.c`

```c
#include "mo_ecat_master_cfg.h"

const struct mo_ecat_master_config g_master_config = {
    .interface_name = "eth0",
};
```

### 10.3 `robot_cfg.h`

```c
#ifndef ROBOT_CFG_H
#define ROBOT_CFG_H

#include "robot_config.h"

extern const struct robot_config g_robot_config;

#endif
```

### 10.4 `robot_cfg.c`

```c
#include "robot_cfg.h"

static const struct robot_joint_config s_joints[] = {
    {
        .joint_name = "left_shoulder_pitch",
        .group      = ROBOT_GROUP_LEFT_ARM,
        .identity   = {
            .position     = 1,
            .vendor_id    = 0x00000766,
            .product_code = 0x00002001,
        },
    },
};

const struct robot_config g_robot_config = {
    .name        = "humanoid",
    .joints      = s_joints,
    .joint_count = sizeof(s_joints) / sizeof(s_joints[0]),
};
```

## 11. 验收条件

验收条件详见《配置系统设计原则.md》第 11 章。核心包括：

- 本机构建与交叉编译均能完成 YAML → C 生成。
- 修改 YAML 后生成器自动重新执行，失败停止构建。
- 目标程序不链接 YAML 解析库、运行时不访问 YAML 文件。
- `CONFIGURE` 后生成有效 PDO 引用和过程映像。
- 任一已发现从站不支持 DC 时 `CONFIGURE` 失败。
- 重新 `DISCOVER`/`CONFIGURE`/`RESET` 后旧 PDO 引用失效。
- `RUNNING` 不触发内存分配、文件 I/O 或日志打印。
