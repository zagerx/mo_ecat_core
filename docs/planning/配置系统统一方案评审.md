# 配置系统统一方案评审

## 总体结论

《配置系统统一方案.md》与《配置系统设计原则.md》目前已在代码生成、YAML 边界、主站自主发现、状态机主路径、DC 检查、过程映像公开视图、generation 失效规则、生成符号链接语义和文档职责划分等方面达成一致。

此前评审项均已处理。当前仅保留以下两项需要明确的接口契约。

## 1. 命令提交结果与异步执行结果需要写入设计原则

状态机命令由 `mo_ecat_master_write_cmd()` 提交，后端动作随后由调度线程异步执行。当前命令表中“失败/无效时返回 -1，状态不变”的表述，容易把两类失败混为一谈：

- **提交失败**：当前状态不允许该命令，或命令参数非法；`mo_ecat_master_write_cmd()` 可以同步返回错误。
- **执行失败**：命令已被接受，但 DISCOVER、CONFIGURE 或 ACTIVATE 的后端动作失败；调用者此前已得到提交成功，后续应通过主站状态、错误码或事件获知 `FAULT`。

《配置系统统一方案.md》已经说明这一契约详见《配置系统设计原则.md》第 7 章，但设计原则当前的命令表仍未写出上述区分。

需要在设计原则中明确两类结果的获取方式，避免应用层把“命令已接受”误解为“总线动作已成功完成”。

## 2. 过程映像视图的并发有效性需要闭合

从站信息与 PDO 引用已经改为“调用方提供缓冲区、核心在锁保护下复制”的查询方式，内部数组指针的生命周期问题已解决。

但 `mo_ecat_master_get_process_image_view()` 仍返回后端 IOmap 的内存指针。文档虽规定 RESET、重新 DISCOVER 或重新 CONFIGURE 后原视图失效，却没有处理并发情形：应用线程正在使用 `view->memory` 时，另一线程执行 RESET 或重新配置，后端可能释放或替换 IOmap，造成悬空访问。

需要明确一种并发策略：

- 由应用层保证在提交 RESET/重新配置前，已停止所有过程映像访问；或
- 主站提供引用计数、读写锁或延迟释放机制，确保旧 IOmap 在读者退出前不被释放；或
- 重新设计过程数据访问接口，使应用不长期持有 IOmap 裸指针。

无论选择哪种，接口文档需要写明并与主站调度线程、应用控制线程的并发模型一致。

---

除以上两项外，当前方案可作为第一阶段实施依据。
