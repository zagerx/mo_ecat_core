# 错误处理与日志设计

## 1. 目的与范围

本文定义 `mo_ecat_core` 的运行期错误处理和日志契约，并作为后续代码改造的依据。

目标不是把每个底层库的返回值直接暴露给应用层，而是做到：

- 状态机能够依据机器可读的错误作出确定的迁移决定；
- 应用层能够取得稳定、平台无关的主站故障类别；
- 开发和现场诊断能够保留足够的底层原因与上下文；
- `RUNNING` 周期路径不分配内存、不格式化字符串、不调用日志回调、不打印；
- SOEM、未来 IGH 等后端遵守同一规则。

本文只讨论核心库的通信、配置和生命周期错误。驱动器对象字典错误、CiA402
状态字、机器人轴组安全策略属于上层设备/机器人模块；核心库只负责提供其传输和
诊断基础。

## 2. 当前实现与问题

当前核心库已经有对外的 `enum mo_ecat_master_error`，状态机能够在扫描、读取 PDO、
配置 DC、建立映射、激活及周期通信失败时进入 `FAULT`。这是正确的基础。

但错误信息仍不完整：

- 大部分内部函数只以 `0/-1` 返回，调用方无法获知具体失败原因；
- `MO_ECAT_MASTER_ERROR_*` 只描述主站级阶段，无法说明后端为何失败；
- SOEM 后端直接使用 `fprintf(stderr, ...)` 和 `printf(...)`；
- 输出位置、格式、级别和是否允许输出都无法统一控制；
- 后端原生错误、从站号、对象索引、WKC 等上下文没有统一承载方式。

因此，错误码应先于日志系统落地。错误码是状态机与应用策略的输入；日志只是错误和
状态变化的可观测输出，不能替代错误码。

## 3. 基本原则

1. **错误与日志分离。** 函数返回详细错误，状态机保存故障；日志记录事件，但日志
   输出失败不得影响主流程。
2. **对外稳定、对内详细。** 应用层使用平台无关的主站错误类别；后端细节只留在
   内部错误记录和日志中。
3. **错误只由发现者产生。** SOEM 发现 `ecx_init()` 失败，就返回“后端打开失败”，
   不由上层猜测底层原因。
4. **状态机负责策略。** 后端不能直接改变 `master->state`；核心状态函数决定该错误
   是进入 `FAULT`、拒绝命令，还是仅记录告警。
5. **快路径零日志。** 周期收发函数不进行 `printf`、文件 I/O、动态内存分配和用户
   日志回调。周期异常只写入已有的周期结果/原子告警标记，由管理路径处理。
6. **错误记录不保存临时字符串指针。** 错误码和数值上下文必须可复制；日志文本在
   输出时生成，不能把栈字符串或后端缓冲区地址保存到主站对象中。

## 4. 错误分层

### 4.1 对外主站错误

现有 `enum mo_ecat_master_error` 保留为公开、稳定的错误分类。应用层通过
`mo_ecat_master_get_error_code()` 读取它，并以此决定 UI 提示、重试或上层安全策略。

建议将其语义收敛为以下类别：

| 对外错误 | 含义 | 典型内部原因 |
|---|---|---|
| `NONE` | 当前没有已发布故障 | 无 |
| `DISCOVER_FAILED` | 打开网口或扫描总线失败 | 网卡不存在、`ecx_init`/`ecx_config_init` 失败 |
| `READ_PDO_DESCRIPTION_FAILED` | PDO 描述读取失败 | SDO 读失败、PDO entry 数超限 |
| `CONFIGURE_DC_FAILED` | DC 配置失败 | 从站不支持 DC、`ecx_configdc` 失败 |
| `CONFIGURE_PDO_MAPPING_FAILED` | 建立 PDO 映射失败 | IOmap 超限、偏移解析失败 |
| `ACTIVATE_FAILED` | 无法进入周期运行 | SAFE-OP/OP 切换失败 |
| `BUS_FAULT` | 周期通信或总线状态异常 | 收发失败、WKC/链路异常 |

公开枚举不应加入 `SOEM_*`、`IGH_*` 或 `ecx_*` 名称，避免把后端选择变成 ABI。

### 4.2 内部详细错误

新增仅供核心层使用的 `enum master_error_detail`，建议放在
`src/master_error.h`。它只描述核心层能够理解的技术原因；核心层函数以它作为详细
返回值，成功为 `MASTER_ERROR_NONE`，失败为非零值。

后端函数**不得**直接返回或依赖 `master_error_detail`。后端应使用独立的
`enum backend_error`，建议放在 `src/backend/backend_error.h`。这样 SOEM 和未来
IGH 只依赖后端契约，不需要包含核心层的 `master_error.h`，也不需要了解主站状态机。

错误层次固定如下：

```text
SOEM / IGH 原生失败
      ↓
backend_error                 后端统一语义
      ↓
master_error_detail           核心层技术原因
      ↓
mo_ecat_master_error           应用层稳定故障类别
```

`backend.c` 或 `master_error.c` 负责把 `backend_error` 映射为
`master_error_detail`。后端原生返回值只写入错误记录的 `native_code`，不能作为公开
ABI，也不能出现在 `backend_error` 的枚举名中。

首批 `backend_error` 建议如下：

```c
enum backend_error {
    BACKEND_ERROR_NONE = 0,
    BACKEND_ERROR_INVALID_ARGUMENT,
    BACKEND_ERROR_NOT_READY,
    BACKEND_ERROR_NO_MEMORY,
    BACKEND_ERROR_OPEN_FAILED,
    BACKEND_ERROR_SCAN_FAILED,
    BACKEND_ERROR_SDO_READ_FAILED,
    BACKEND_ERROR_PDO_ENTRY_LIMIT_EXCEEDED,
    BACKEND_ERROR_DC_UNSUPPORTED,
    BACKEND_ERROR_DC_CONFIG_FAILED,
    BACKEND_ERROR_PDO_MAPPING_FAILED,
    BACKEND_ERROR_PDO_IMAGE_TOO_LARGE,
    BACKEND_ERROR_PDO_OFFSET_RESOLVE_FAILED,
    BACKEND_ERROR_ACTIVATE_FAILED,
    BACKEND_ERROR_CYCLIC_RECEIVE_FAILED,
    BACKEND_ERROR_CYCLIC_SEND_FAILED,
};
```

首批错误码建议如下：

```c
enum master_error_detail {
    MASTER_ERROR_NONE = 0,

    MASTER_ERROR_INVALID_ARGUMENT,
    MASTER_ERROR_INVALID_STATE,
    MASTER_ERROR_NO_MEMORY,

    MASTER_ERROR_BACKEND_OPEN_FAILED,
    MASTER_ERROR_BUS_SCAN_FAILED,
    MASTER_ERROR_READ_PDO_ASSIGNMENT_FAILED,
    MASTER_ERROR_PDO_ENTRY_LIMIT_EXCEEDED,
    MASTER_ERROR_DC_UNSUPPORTED,
    MASTER_ERROR_DC_CONFIG_FAILED,
    MASTER_ERROR_PDO_IMAGE_LIMIT_EXCEEDED,
    MASTER_ERROR_PDO_MAPPING_FAILED,
    MASTER_ERROR_PDO_OFFSET_RESOLVE_FAILED,
    MASTER_ERROR_ACTIVATE_FAILED,
    MASTER_ERROR_CYCLIC_RECEIVE_FAILED,
    MASTER_ERROR_CYCLIC_SEND_FAILED,
};
```

该枚举描述“失败的技术原因”，而不是状态机动作。例如
`BACKEND_ERROR_DC_UNSUPPORTED` 会先映射为 `MASTER_ERROR_DC_UNSUPPORTED`，但两者都
不等同于 `FAULT`；IDLE 状态最终将它映射为 `CONFIGURE_DC_FAILED` 并进入 `FAULT`。

### 4.3 错误记录

主站内部保存最近一次导致故障的完整记录，而不是只保存公开错误码：

```c
enum master_error_source {
    MASTER_ERROR_SOURCE_CORE,
    MASTER_ERROR_SOURCE_BACKEND,
    MASTER_ERROR_SOURCE_SOEM,
};

struct master_error_record {
    enum mo_ecat_master_error master_error; /* 对外故障类别 */
    enum master_error_detail detail;        /* 内部技术原因 */
    enum master_error_source source;        /* 产生错误的模块 */
    int native_code;                        /* 后端原生返回值；无则为 0 */
    size_t slave_index;                      /* 无特定从站时为 SIZE_MAX */
    uint16_t object_index;                  /* 无对象上下文时为 0 */
    uint8_t object_subindex;                /* 无对象上下文时为 0 */
};
```

此结构在第一阶段只由 dispatch 线程读写。对外仍只发布
`mo_ecat_master_error`；若以后需要跨线程读取详细记录，应通过不可变快照接口发布，
不能直接把内部结构暴露给应用层。

## 5. 错误传播与状态机映射

错误传播方向必须固定：

```text
SOEM/IGH 原生失败
      ↓
backend 返回 backend_error 与上下文
      ↓
核心层将 backend_error 映射为 master_error_detail，并补充或透传上下文
      ↓
状态函数记录 master_error_record
      ↓
映射为 mo_ecat_master_error，执行 sm_transition(..., FAULT)
      ↓
应用层读取 state / mo_ecat_master_get_error_code()
```

示例：

```text
ecx_config_map_group() 返回失败，或映射大小超过 IOmap 容量
  → MASTER_ERROR_PDO_IMAGE_LIMIT_EXCEEDED
  → MO_ECAT_MASTER_ERROR_CONFIGURE_PDO_MAPPING_FAILED
  → master_state_idle() 进入 FAULT
```

状态机中建议统一使用一个内部函数完成记录与迁移：

```c
static void master_fault(struct statemachine *sm,
                         struct mo_ecat_master *master,
                         enum mo_ecat_master_error master_error,
                         const struct master_error_record *record);
```

该函数只能处理固定收尾：写入错误记录、释放资源、调用 `sm_transition()`。它不应
包含后端调用、日志格式化或额外的恢复策略。

命令提交失败和命令执行失败必须区分：

- `mo_ecat_master_write_cmd()` 同步失败：参数非法或当前状态不允许该命令；函数直接
  返回失败，不改变主站已发布故障。
- 已接受命令后异步执行失败：状态机记录错误并进入 `FAULT`；应用层随后读取状态和
  主站错误码。

## 6. 日志系统设计

### 6.1 职责

日志系统只负责事件输出，不负责状态保存和错误传播。日志应覆盖：

- 后端打开、扫描、PDO 描述读取、DC 配置、映射、激活和关闭；
- 所有状态迁移；
- 命令接受、拒绝及执行失败；
- 进入 `FAULT` 时的公开错误码、内部详细错误和可用上下文；
- 管理路径中的从站号、对象索引、IOmap 大小、期望/实际 WKC 等诊断数据。

### 6.2 最小内部接口

第一阶段只实现内部通用接口，放在 `src/common/log/log.h/.c`。日志模块不引用
`master_error.h`，SOEM/IGH 只能依赖该通用设施与 `backend_error`，不依赖主站核心层：

```c
enum core_log_level {
    CORE_LOG_DEBUG,
    CORE_LOG_INFO,
    CORE_LOG_WARN,
    CORE_LOG_ERROR,
};

void core_log_write(enum core_log_level level,
                    const char *module,
                    const char *format, ...);
```

日志框架尚未实现前，核心层和后端不输出临时文本，不调用 `printf` 或 `fprintf`；
只返回错误码并更新错误记录。后续异步日志框架实现后，由日志模块提供 sink，支持
应用注册的 sink、syslog、文件轮转或结构化事件，而无需修改后端错误处理。

第一阶段不要求在公开 API 暴露日志回调。等线程模型、部署环境和日志线程策略稳定后，
再设计公开 sink 注册接口。

### 6.3 实时边界

| 路径 | 是否允许同步日志 | 规则 |
|---|---:|---|
| INIT / IDLE / READY / FAULT 管理动作 | 是 | 可记录状态、命令和配置错误 |
| SCAN / PDO 读取 / DC / 映射 | 是 | 可记录后端和配置上下文 |
| RUNNING 正常每周期 | 否 | 不记录成功收发或普通周期数据 |
| RUNNING 周期异常 | 否 | 仅更新已有错误/告警数据；由后续管理路径输出 |
| 销毁与资源释放 | 是 | 仅在非实时上下文调用 |

特别地，不允许为了“打印周期错误”在 `master_state_running()` 内调用日志 sink。若要
保留 WKC、时间戳等异常信息，应预先分配固定大小的诊断快照，由非实时线程读取并输出。

## 7. 改造步骤

### 阶段 1：统一内部错误码

1. 新增 `src/backend/backend_error.h`，定义独立的 `backend_error`；SOEM 和未来 IGH
   仅通过它向核心层报告后端失败。
2. 新增 `src/master_error.h/.c`，定义 `master_error_detail`、错误记录，以及
   `backend_error` 到核心详细错误、核心详细错误到公开主站错误的映射。
3. 逐步把 `backend_*` 的 `0/-1` 返回值改为 `backend_error`，把
   `slave_table_*`、`pdo_layout_*` 的返回值改为 `master_error_detail`。
4. SOEM 后端在失败处返回精确错误：网口打开、扫描、SDO 读取、DC 不支持、DC 配置、
   IOmap 上限、映射解析、激活、周期收发。
5. 状态函数记录详细错误并统一迁移到 `FAULT`。
6. 保持公开 `mo_ecat_master_error` 与现有 `mo_ecat_master_get_error_code()` 的兼容性。

### 阶段 2：实现异步日志并接入管理路径

当前需替换的直接输出位于：

- `src/backend/soem/soem_discovery.c`：`ecx_init()`、`ecx_config_init()` 失败；
- `src/backend/soem/soem_mapping.c`：DC 不支持、`ecx_configdc()`、IOmap 建立失败及
  映射成功提示。

实现异步日志框架后，这些位置写入非实时日志队列，并同时返回对应的
`backend_error`；不能只记录文本后继续返回笼统 `-1`。

### 阶段 3：状态与故障日志

1. 在唯一的状态迁移入口记录“旧状态、目标状态、触发命令或错误码”。
2. 在进入 `FAULT` 时记录一次完整 `master_error_record`。
3. 避免在多处对同一错误重复打印；一条错误应由错误产生点或故障迁移点确定唯一日志
   责任，推荐后者输出完整汇总。

### 阶段 4：可选诊断快照

当需要从非实时线程读取运行期详细信息时，新增固定大小或双缓冲快照，而非在
`RUNNING` 加锁或动态分配。该阶段可加入 WKC 异常、从站 AL 状态、周期时间和 SDO
维护任务结果。

## 8. 验收标准

- 核心库和后端不再直接调用 `printf`、`fprintf` 或 `perror`。
- 每一个可进入 `FAULT` 的路径都能给出一个公开主站错误和一个内部详细错误。
- 同一故障在日志中能够定位到模块、失败阶段及可用的从站/PDO 上下文。
- 应用层无需依赖 SOEM/IGH 头文件即可依据公开主站错误做策略。
- `RUNNING` 的正常与异常路径均不进行日志输出、内存分配或阻塞 I/O。
- 错误处理改造后，现有扫描、配置、激活、复位和销毁资源释放语义不改变。

## 9. 非目标

- 本阶段不实现文件轮转、网络日志上传或日志持久化策略。
- 本阶段不定义机器人关节、轴组、驱动器厂商错误码的统一解释。
- 本阶段不将 SOEM 原生错误枚举直接暴露为公开 ABI。
- 本阶段不以日志替代故障快照、状态机迁移或应用层安全策略。
