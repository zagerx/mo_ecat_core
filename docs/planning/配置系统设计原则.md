# mo_ecat_core 配置系统设计原则

> 本文档记录配置系统的最终设计原则，是代码实现、代码审查和未来扩展的判定依据。内容已根据项目讨论最终确定，不再随意变更。

---

## 1. 目的与范围

本设计原则适用于 `mo_ecat_core` 项目的配置系统，定义：

- 人工维护配置如何进入系统；
- 主站、后端、机器人应用之间的配置边界；
- 配置系统在构建期、启动期、运行期的行为约束；
- 生成器、CMake、状态机、应用接口必须遵守的契约。

**范围边界**：本文档只规定第一阶段设计。运行期 YAML 加载、动态 PDO 重映射、多主站/多机器人、系统级策略文件等作为后续扩展，不在本文档范围内。

---

## 2. 总体原则

### 2.1 代码生成原则

- YAML 是人工维护的唯一源文件。
- 宿主机代码生成器 `mo_ecat_config_gen` 在构建期将 YAML 转换为 `.c/.h`。
- 目标程序运行时不解析 YAML、不访问 YAML 文件、不链接 YAML 解析库。
- 生成的 `.c/.h` 文件是构建产物，**禁止人工修改**。

### 2.2 YAML 单一来源原则

- 产品/应用层可变配置收敛到 YAML。
- 后端编译参数（如 IOmap 容量、超时）由 CMake/代码宏管理，**不进入 YAML**。
- 从站身份信息**只出现在 `robot.yaml` 中**，不出现在 `master.yaml` 中。

### 2.3 主站自主发现原则

- 主站在运行期主动扫描总线，获取真实从站信息。
- PDO 映射、DC 能力、从站身份等必须由主站向从站查询，**不能从配置文件加载**。
- 主站 `CONFIGURE` 阶段使用扫描到的真实数据完成总线配置。

### 2.4 机器人身份标准原则

- `robot.yaml` 中的 `joints[].identity`（`position`、`vendor_id`、`product_code`）是机器人关节的权威标准。
- 机器人模块 `robot_build()` 使用主站扫描结果与 `robot.yaml` 比对， mismatch 直接报错。
- 机器人模块不依赖 `master.yaml` 中的从站描述。

### 2.5 核心零 YAML 运行时原则

- 核心库 `mo_ecat_core` 只消费 C 数据模型和扫描结果，不依赖 YAML 格式、文件 I/O 或解析器。
- 机器人应用库 `mo_robot` 只消费 `robot_config`，不直接读取 YAML。

### 2.6 后端与平台边界原则

- 后端类型由 CMake/构建目标固定，运行期不可切换。
- 后端专有参数由 CMake 选项或代码宏提供，不通过 YAML 配置。
- 应用层不依赖后端专有数据结构。

### 2.7 配置与构建分离原则

- `src/config/master.yaml` 属于核心库主站配置，生成产物编译进核心库。
- `examples/cli/config/robot.yaml` 属于 CLI 机器人配置。
- 生成器可以同时读取两份 YAML；核心库不持有机器人配置，CLI 不读取主站配置。

## 3. 配置分层与文件职责

### 3.1 文件划分

| 文件 | 职责 | 归属 |
|---|---|---|
| `src/config/master.yaml` | 只包含主站网口名 `interface` | 核心库主站配置 |
| `examples/cli/config/robot.yaml` | 机器人名称、关节、功能组、从站身份 | CLI 机器人配置 |

### 3.2 `master.yaml` 唯一允许的内容

```yaml
version: "1.0"
master:
  interface: "eth0"
```

- 不允许出现 `cycle_time_us`、`dc_enabled`、`backend_type`。
- 不允许出现 `bus.slaves`、`backend`、`pdo_entries` 等任何从站或后端描述。

### 3.3 `robot.yaml` 允许的内容

```yaml
version: "1.0"
robot:
  name: "humanoid"
  joints:
    - joint_name: "left_shoulder_pitch"
      group: "left_arm"
      identity:
        position: 1
        vendor_id: 0x00000766
        product_code: 0x00002001
```

- `joint_name`：必填，关节逻辑名，机器人模块内唯一。
- `group`：必填，必须是已定义的 `robot_group_id` 字符串。
- `identity.position`/`vendor_id`/`product_code`：必填，用于和主站扫描结果比对。

## 4. C 数据模型

### 4.1 主站启动选项

```c
struct mo_ecat_master_config {
    char interface_name[MO_ECAT_MAX_IFNAME_LEN + 1];
};
```

- 只保留网口名。
- 由 `src/config/master.yaml` 生成并编译进核心库。

### 4.2 机器人配置

```c
struct robot_slave_identity {
    uint16_t position;
    uint32_t vendor_id;
    uint32_t product_code;
};

struct robot_joint_config {
    const char *joint_name;
    enum robot_group_id group;
    struct robot_slave_identity identity;
};

struct robot_config {
    const char *name;
    const struct robot_joint_config *joints;
    size_t joint_count;
};
```

- 由 `examples/cli/config/robot.yaml` 生成。
- 生成的内部数组使用 `static const`；核心库内部使用 `g_master_config`，CLI 使用自己的机器人配置实现。

### 4.3 已删除的模型

以下结构在第一阶段不再存在：

- `mo_ecat_user_config`
- `mo_ecat_slave_config`
- `mo_ecat_pdo_entry_config`

主站不再从配置中读取预期从站、PDO 条目或 DC 开关。

## 5. 生成器契约

### 5.1 输入输出

生成器 `mo_ecat_config_gen` 命令行：

```bash
mo_ecat_config_gen \
  --master-yaml src/config/master.yaml \
  --robot-yaml examples/cli/config/robot.yaml \
  --master-out-c build/generated/mo_ecat_master_cfg.c \
  --master-out-h build/generated/mo_ecat_master_cfg.h \
  --robot-out-c  build/generated/robot_cfg.c \
  --robot-out-h  build/generated/robot_cfg.h
```

### 5.2 版本规则

- YAML 顶层必须包含 `version: "major.minor"`。
- 生成器只支持已声明的主版本；主版本不匹配直接报错。
- 小版本向后兼容。

### 5.3 错误格式

```
[ERROR] <file>:<line>:<col> <field_path>: <reason> (expected: ..., actual: ...)
```

### 5.4 校验规则

#### 5.4.1 `master.yaml`

- 只允许 `version` 和 `master.interface`。
- `interface` 必填且非空。
- 任何其他字段直接报错。

#### 5.4.2 `robot.yaml`

- `robot.name` 必填且非空。
- `joints[]` 中每个元素必须包含 `joint_name`、`group`、`identity`。
- `identity` 必须包含 `position`、`vendor_id`、`product_code`。
- `joint_name` 在文件内唯一。
- `(position, vendor_id, product_code)` 三元组在文件内唯一。
- `group` 字符串必须在生成器的固定映射表中。
- `joint_count <= MO_ROBOT_MAX_JOINTS`。

### 5.5 输出格式

- 文件头包含：
  ```c
  /* Auto-generated by mo_ecat_config_gen from <yaml_path> */
  /* DO NOT EDIT MANUALLY */
  ```
- 跨编译单元访问的内部主站配置 `g_master_config` 使用外部链接的 `const`。
- 仅在单一文件内部使用的数组使用 `static const`。
- 头文件声明与实现文件定义必须一致。

## 6. CMake 与构建契约

### 6.1 本机构建

```cmake
add_executable(mo_ecat_config_gen tools/config_gen/main.c ...)
target_link_libraries(mo_ecat_config_gen yaml)

add_custom_command(
    OUTPUT ...
    COMMAND $<TARGET_FILE:mo_ecat_config_gen> ...
    DEPENDS mo_ecat_config_gen ...
)
```

### 6.2 交叉编译/嵌入式构建

生成器不能按普通目标程序交叉编译。必须采用以下策略之一：

1. **预编译宿主机工具**：环境变量 `MO_ECAT_CONFIG_GEN` 指向宿主机可执行文件。
2. **独立宿主机构建**：`ExternalProject_Add` 或单独 host 工具链编译生成器。
3. **预生成 C 文件**：在交叉编译前运行生成器，产物放入 `src/generated/`，嵌入式构建直接编译。

`add_custom_command()` 执行的必须是能在构建主机上运行的实际路径。

### 6.3 产物目录

- 常规构建：`build/generated/`。
- 嵌入式预生成：`src/generated/`。
- 预生成产物仍为生成物，禁止人工修改。

## 7. 状态机契约

### 7.1 状态定义

稳定状态：
- `INIT`
- `IDLE`
- `READY`
- `RUNNING`
- `FAULT`

内部过渡状态（不对外公开）：
- `SCANNING`
- `CONFIGURING`
- `ACTIVATING`

### 7.2 状态流转

```
INIT → IDLE → CONFIGURING → READY → ACTIVATING → RUNNING
           ↑_________↓   ↓_________↓          ↓________↓
           └───────────────────────────────────────────┘
                              FAULT
```

### 7.3 命令合法来源与失败行为

| 命令 | 合法来源状态 | `write_cmd` 返回值 | 执行失败结果 |
|---|---|---|---|
| `DISCOVER` | `IDLE` | `0` 已接受；`-1` 状态/参数非法 | 进入 `FAULT`，可通过 `get_last_error()` 查询 |
| `CONFIGURE` | 扫描完成后的 `IDLE` | `0` 已接受；`-1` 状态/参数非法 | 进入 `FAULT`，可通过 `get_last_error()` 查询 |
| `ACTIVATE` | `READY` | `0` 已接受；`-1` 状态/参数非法 | 进入 `FAULT`，可通过 `get_last_error()` 查询 |
| `DEACTIVATE` | `RUNNING` | `0` 已接受；`-1` 状态/参数非法 | 进入 `FAULT`，可通过 `get_last_error()` 查询 |
| `RESET` | 除 `INIT` 外均可 | `0` 已接受；`-1` 参数非法 | 释放运行资源，进入 `IDLE`；无额外执行失败 |

### 7.4 失败后目标状态

- `DISCOVER` 失败 → `FAULT`。
- `CONFIGURE` 失败 → `FAULT`。
- `ACTIVATE` 失败 → `FAULT`。
- `FAULT` 后必须 `RESET` 才能回到 `IDLE`，并重新 `DISCOVER`/`CONFIGURE`。

### 7.5 资源释放责任

- `RESET` 释放扫描结果、PDO 引用表、IOmap 和过程映像。
- `DEACTIVATE` 只停止周期运行，保留已配置的 PDO/IOmap 资源。
- 重新 `DISCOVER`/`CONFIGURE` 后，旧 PDO 引用必须失效。

## 8. PDO、DC 与过程映像

### 8.1 PDO 来源

- PDO 映射由主站在 `CONFIGURING` 阶段读取各从站默认 PDO 映射获得。
- 不从 YAML 加载 PDO 条目，也不允许 YAML 描述 PDO 子集。

### 8.2 DC 规则

- 系统总是尝试启用 DC 同步。
- **所有**已发现从站（包括非机器人从站）必须支持 DC；任一不支持，`CONFIGURE` 失败。
- `mo_ecat_master_config` 中不存在 `dc_enabled` 开关。

### 8.3 IOmap 与后端参数

- IOmap 大小、SDO 超时等由后端宏或 CMake 选项定义。
- YAML 中不出现任何后端专有参数。

### 8.4 应用层 PDO 查询接口

应用层通过主站公开 API 获取从站信息、PDO 引用和过程映像。为避免返回内部数组指针的生命周期问题，从站信息和 PDO 引用采用**调用方提供缓冲区、核心在锁保护下复制**的方式返回；过程映像以公开只读视图返回，不暴露内部 `mo_ecat_process_image` 结构：

```c
struct mo_ecat_process_image_view {
    const uint8_t *memory;
    size_t         size;
    uint32_t       generation;
};

size_t mo_ecat_master_get_slave_count(const struct mo_ecat_master *master);

int mo_ecat_master_get_slave_info(
    const struct mo_ecat_master *master,
    size_t slave_index,
    struct mo_ecat_slave_info *info);

int mo_ecat_master_get_pdo_ref(
    const struct mo_ecat_master *master,
    size_t slave_index, uint16_t index, uint8_t subindex,
    enum mo_ecat_pdo_direction direction,
    struct mo_ecat_pdo_ref *ref);

int mo_ecat_master_get_process_image_view(
    const struct mo_ecat_master *master,
    struct mo_ecat_process_image_view *view);
```

- `mo_ecat_master_get_slave_info()` 与 `mo_ecat_master_get_pdo_ref()` 由调用方提供缓冲区，核心在持有主站锁期间复制数据，返回后应用可安全使用缓冲区内容。
- `view->memory` 和 `view->size` 描述当前活动的过程映像。
- `view->generation` 与 `mo_ecat_pdo_ref.generation` 比较，判断引用是否属于当前过程映像。

### 8.5 代际失效规则

- 主站对象维护一个单调递增的 `generation`（或 `epoch`），在每次 `CONFIGURE` 成功时递增。
- `generation` 在主站整个生命周期内只增不减；`RESET` 不清零。
- `mo_ecat_pdo_ref.generation` 与当前 `image.generation` 不一致时，引用失效，必须重新查询。
- `RESET` 后所有引用失效；`DEACTIVATE` 不导致失效。
- `generation` 溢出时，所有已有 PDO 引用视为失效，应用层必须重新查询。

### 8.6 内部指针生命周期

- `mo_ecat_master_get_slave_info()` 和 `mo_ecat_master_get_pdo_ref()` 不返回内部数组指针，因此不存在跨状态迁移的悬空指针问题。
- `mo_ecat_master_get_process_image_view()` 返回的 `view->memory` 指向后端 IOmap 缓冲区。该指针仅在以下条件下有效：
  - 当前主站状态为 `READY` 或 `RUNNING`；
  - 自获取视图后未发生 `RESET`、重新 `DISCOVER` 或重新 `CONFIGURE`。
- 一旦触发可能替换 IOmap 的状态迁移，原有视图立即失效，应用层必须重新调用 `mo_ecat_master_get_process_image_view()` 获取新视图。

#### 8.6.1 过程映像视图的并发有效性

- `mo_ecat_master_get_process_image_view()` 返回的指针指向后端 IOmap 内部缓冲区，存在被调度线程释放或替换的风险。
- 第一阶段采用**应用层责任模型**：应用线程在提交 `RESET`、重新 `DISCOVER` 或重新 `CONFIGURE` 命令前，必须先停止所有对过程映像视图的访问，并放弃已保存的视图指针。
- 主站在完成 `RESET`、重新 `DISCOVER` 或重新 `CONFIGURE` 后，不保证旧 IOmap 缓冲区的继续有效，也不提供引用计数或延迟释放。
- 后续如需多线程并发访问过程映像，可引入引用计数、读写锁、周期回调或拷贝接口，但不在第一阶段实现。

## 9. 运行时资源边界

| 阶段 | 允许行为 | 禁止行为 |
|---|---|---|
| 生成器运行期 | 动态分配、文件 I/O、YAML 解析 | 生成不符合 C 模型的输出 |
| 主站创建期 | 分配主站对象、初始化互斥锁 | 访问总线 |
| `DISCOVER` | 分配扫描结果/诊断数组 | 配置 PDO/DC |
| `CONFIGURING` | 读取 PDO、检查 DC、分配 PDO 引用表、建立 IOmap | 无 |
| `RUNNING` | 周期数据交换、诊断读取 | 内存分配、文件 I/O、YAML、阻塞打印 |

## 10. CLI 与 Fallback 规则

### 10.1 CLI 行为

- CLI 不接收运行时 YAML 路径。
- CLI 不接收运行时网口覆盖参数。
- 配置在构建期固化；核心库内部引用生成的主站配置，CLI 只引用机器人配置。

### 10.2 Fallback

- 硬编码默认配置（`robot_default_config()`、`g_options` 默认值）仅用于示例/测试。
- 产品构建必须启用代码生成；生成失败必须阻止构建。
- 默认配置不允许作为产品构建的静默 fallback。
- 示例/测试 fallback 通过独立 CMake 选项或独立 example target 启用。

---

## 11. 验收条件

- 本机构建与交叉编译均能在构建主机完成 YAML → C 生成。
- 修改 YAML 后，生成器自动重新执行，且生成失败会停止构建。
- 生成后的目标程序不链接 YAML 解析库、运行时不访问 YAML 文件。
- 配置字段错误能定位到文件、行列和字段路径。
- `DISCOVER` 后可查询所有从站，`CONFIGURE` 后才生成有效 PDO 引用和过程映像。
- 任一已发现从站（包括非机器人从站）不支持 DC 时，`CONFIGURE` 失败且不进入 `READY`。
- 重新 `DISCOVER`、`CONFIGURE` 或 `RESET` 后，旧 PDO 引用被拒绝。
- `RUNNING` 路径不触发内存分配、文件 I/O 或日志打印。
