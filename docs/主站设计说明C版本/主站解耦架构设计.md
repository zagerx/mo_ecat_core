# EtherCAT 主站解耦架构设计

## 1. 设计目标

本方案用于将 `mo_ecat` 的主站逻辑与 SOEM、IGH 等 EtherCAT 主站库解耦。核心层不以某个后端的数据结构为模板，而是定义一组能被不同后端自然实现的最小契约。

设计目标：

- 核心层头文件不包含 `soem.h`、`ecrt.h` 或任何后端类型。
- 核心层使用自有的配置、状态、错误和周期结果类型。
- 主站以“配置驱动”运行，在线发现只是辅助配置和校验总线的工具。
- 实时周期明确分为接收和发送两个阶段。
- 统一所有后端必须具备的能力，后端特有能力通过可选扩展提供。
- 明确过程数据域的所有权、有效期和重新配置规则。
- 主站全生命周期必须由 `statemachine.c/.h` 驱动状态切换，禁止在业务流程中散落直接赋值状态。
- 保留现有 `ec_master_*` 公共 API 作为兼容层，避免一次性破坏应用代码。

## 2. 设计原则

### 2.1 配置驱动，发现辅助

SOEM 适合先扫描总线再建立映射，IGH 则更适合根据预先声明的从站和 PDO 配置创建 slave config 与 domain。因此，公共运行流程以平台无关配置为输入：

```text
加载配置 → 打开后端 → 可选发现/校验 → 配置映射 → 激活 → 周期运行
```

发现结果不直接决定实时映射，而是用于：

- 生成初始配置；
- 校验实际总线与期望配置是否一致；
- 向诊断工具展示未配置的设备。

### 2.2 最小公共能力

公共 backend 接口只包含 SOEM 和 IGH 都能稳定实现的能力。例如，SOEM 可通过 `ecx_writestate()` 主动请求任意 AL 状态，而 IGH 通常由内部状态机根据激活和配置自动驱动从站。因此，“手动 AL 状态控制”不是公共必选能力，而是可选扩展。

### 2.3 快路径与管理路径分离

- 快路径：`cycle_begin()` / `cycle_end()`，不分配内存、不输出日志、不执行阻塞状态等待。
- 管理路径：发现、配置、激活、状态诊断、错误恢复。

### 2.4 状态机统一托管主站生命周期

主站从创建到销毁必须始终处于一个明确状态下。核心层使用 `src/common/statemachine/statemachine.c/.h` 作为主站生命周期状态机框架：

- `struct mo_ecat_master` 内部持有 `struct statemachine sm`。
- `enum mo_ecat_master_state` 是对外可观测的状态 ID。
- 状态 ID 只能在状态函数的 `ENTER` 阶段更新。
- 所有状态迁移必须由状态函数调用 `sm_transition()` 触发，禁止业务代码直接写 `master->state = ...`。
- 非法迁移必须被拒绝并返回错误。
- 状态函数负责进入动作、退出动作和必要的运行期动作；管理 API 只提交命令，后端 open/configure/activate/deactivate 等动作由对应状态函数分阶段执行。

## 3. 总体架构

```text
应用层
  ├─ 设备与 PDO 配置
  ├─ 实时控制算法
  └─ 管理与诊断
             │
             ▼
┌─────────────────────────────────────────┐
│ mo_ecat 核心层（平台无关）        │
│ - 配置模型与总线校验               │
│ - 主站生命周期与故障策略           │
│ - 过程数据域与 PDO 引用             │
│ - 两阶段实时周期                     │
└─────────────────────────────────────────┘
             │ backend ops
       ┌─────────────┴─────────────┐
       ▼                           ▼
┌──────────────────┐         ┌──────────────────┐
│ SOEM backend     │         │ IGH backend      │
│ ecx_contextt     │         │ master/domain/sc │
└──────────────────┘         └──────────────────┘
```

## 4. 平台无关配置模型

### 4.1 PDO 配置

```c
enum mo_ecat_pdo_direction {
    MO_ECAT_PDO_INPUT,
    MO_ECAT_PDO_OUTPUT
};

struct mo_ecat_pdo_entry_config {
    uint16_t index;
    uint8_t  subindex;
    uint8_t  bit_length;
    enum mo_ecat_pdo_direction direction;
};

struct mo_ecat_dc_config {
    int      enabled;
    uint32_t assign_activate;
    uint32_t sync0_cycle_ns;
    int32_t  sync0_shift_ns;
};
```

### 4.2 从站配置

```c
struct mo_ecat_slave_config {
    uint16_t alias;
    uint16_t position;

    uint32_t vendor_id;
    uint32_t product_code;
    uint32_t revision_number;

    const char *name;            /* 可选，用于配置与诊断展示 */

    const struct mo_ecat_pdo_entry_config *pdo_entries;
    size_t pdo_entry_count;

    int dc_active;               /* 该从站是否参与 DC */
};

struct mo_ecat_config {
    const char *interface_name;

    const struct mo_ecat_slave_config *slaves;
    size_t slave_count;
};
```

`position` 是物理总线位置，不等于核心层数组下标。核心层从站数组统一使用 0-based 下标，不使用第 0 个元素表示广播。

核心配置不包含 IOmap 容量、IGH master index 等后端专有选项。这些选项必须通过各后端的强类型初始化接口传入，不在 `mo_ecat_config` 中放置通用 `void *backend_options`。

## 5. 核心运行时模型

### 5.1 AL 状态

AL 基础状态与错误标志分开表示，因为 EtherCAT 可能同时处于 `SAFE_OP` 和错误状态。

```c
enum mo_ecat_al_state {
    MO_ECAT_AL_STATE_INIT,
    MO_ECAT_AL_STATE_PRE_OP,
    MO_ECAT_AL_STATE_SAFE_OP,
    MO_ECAT_AL_STATE_OP,
    MO_ECAT_AL_STATE_BOOTSTRAP,
    MO_ECAT_AL_STATE_UNKNOWN
};

struct mo_ecat_slave_state {
    enum mo_ecat_al_state al_state;
    int                   error;
    uint16_t              al_status_code;
    int                   online;
    int                   operational;
};
```

### 5.2 从站对象

```c
struct mo_ecat_slave {
    uint16_t position;           /* 物理总线位置 */
    uint16_t alias;

    uint32_t vendor_id;
    uint32_t product_code;
    uint32_t revision_number;

    char name[MO_ECAT_MAX_NAME_LEN + 1];
    struct mo_ecat_slave_state state;

    int     has_dc;
    int32_t propagation_delay_ns;
};
```

后端私有的 SOEM slave 下标、IGH `ec_slave_config_t *` 等对象不放入 `mo_ecat_slave`，而由 `backend->ctx` 按核心层从站下标建立对应表。

### 5.3 过程数据域与 PDO 引用

```c
struct mo_ecat_process_image {
    uint8_t *memory;
    size_t   size;
    uint32_t generation;
    int      active;
};

struct mo_ecat_pdo_ref {
    size_t   slave_index;        /* 所属从站在核心层数组中的下标 */
    uint16_t pdo_index;          /* PDO 索引（对应 entry_config.index） */
    uint16_t entry_index;        /* 子索引（对应 entry_config.subindex） */

    uint32_t byte_offset;
    uint8_t  bit_offset;
    uint8_t  bit_length;
    enum mo_ecat_pdo_direction direction;
    uint32_t generation;
};
```

当前版本只支持一个过程数据域，不在对象模型中伪装多域能力。如果后续确实需要多周期或多 domain，再将它扩展为 domain 数组。

PDO 引用通过 offset 而非长期裸指针表示。获取数据地址时必须校验 generation：

```c
const void *mo_ecat_pdo_input(const struct mo_ecat_master *master,
                              const struct mo_ecat_pdo_ref *ref);

void *mo_ecat_pdo_output(struct mo_ecat_master *master,
                         const struct mo_ecat_pdo_ref *ref);
```

两个访问函数同时校验 offset 边界、generation 和 direction。输入接口返回 `const void *`，输出接口才返回可写指针，避免应用层误写输入区。

激活后允许应用缓存返回的指针以避免实时周期内的额外查询，但必须遵守：运行期间禁止重新配置，且在 generation 变化后重新获取所有指针。

### 5.4 周期结果

```c
struct mo_ecat_cycle_result {
    int      backend_error;      /* 后端原始错误，仅用于诊断 */
    int      link_up;

    uint32_t expected_wkc;
    uint32_t actual_wkc;

    int64_t  dc_time_ns;
    int      dc_time_valid;

    int      diagnostics_required;
};
```

`cycle_begin()` 和 `cycle_end()` 的阶段状态由各自的 `int` 返回值表示，不共享一个可能被覆盖的 `result.status`。`backend_error` 保留本周期观察到的第一个后端错误，后续阶段不得覆盖它。

`diagnostics_required` 表示快路径观察到 WKC、链路或 domain 状态异常，需要管理路径执行详细诊断。它不承诺每周期都能精确检测所有从站 AL 状态变化。

## 6. Backend 契约

### 6.1 能力声明

```c
struct mo_ecat_backend_caps {
    int online_discovery;
    int dynamic_pdo_mapping;
    int dc_support;
    int redundancy;
    int manual_state_control;
};
```

### 6.2 最小必选操作表

```c
struct mo_ecat_backend;
struct mo_ecat_discovery_ops;
struct mo_ecat_manual_state_ops;

struct mo_ecat_backend_ops {
    const char *name;

    int  (*open)(struct mo_ecat_backend *backend,
                 const struct mo_ecat_config *config);

    int  (*configure)(struct mo_ecat_backend *backend,
                      const struct mo_ecat_config *config,
                      struct mo_ecat_process_image *image,
                      struct mo_ecat_pdo_ref *pdo_refs,
                      size_t pdo_ref_count,
                      struct mo_ecat_slave *slaves,
                      size_t slave_count);

    int  (*activate)(struct mo_ecat_backend *backend);

    /* 接收并处理本周期输入 */
    int  (*cycle_begin)(struct mo_ecat_backend *backend,
                        struct mo_ecat_cycle_result *result);

    /* 提交并发送本周期输出 */
    int  (*cycle_end)(struct mo_ecat_backend *backend,
                      struct mo_ecat_cycle_result *result);

    int  (*read_diagnostics)(struct mo_ecat_backend *backend,
                             struct mo_ecat_slave_state *states,
                             size_t state_count);

    int  (*deactivate)(struct mo_ecat_backend *backend);
    void (*close)(struct mo_ecat_backend *backend);
};

struct mo_ecat_backend {
    const struct mo_ecat_backend_ops *ops;
    const struct mo_ecat_discovery_ops *discovery_ops;       /* 可为 NULL */
    const struct mo_ecat_manual_state_ops *manual_state_ops; /* 可为 NULL */
    struct mo_ecat_backend_caps caps;
    void *ctx;
};
```

`open()`、`configure()` 和 `activate()` 必须可以在失败后通过 `close()` 安全回滚；`deactivate()` 和 `close()` 应对重复调用安全。`deactivate()` 失败时核心层记录“未能安全停机”错误，但仍必须继续调用 `close()` 释放资源。

### 6.3 PDO 引用分配与映射契约

- `pdo_refs` 由核心层在管理路径分配和释放。
- `pdo_ref_count` 等于所有 `config->slaves[i].pdo_entry_count` 之和。
- 引用顺序与配置的扁平遍历顺序一致：先按 `slaves[]` 顺序，再按每个从站的 `pdo_entries[]` 顺序。
- 核心层根据配置预填充 bit length 和 direction；backend 按相同顺序验证并填写 byte/bit offset。
- `configure()` 整体成功后，核心层再提交新的 image generation，并统一写入所有 PDO 引用；失败时不发布部分映射结果。
- 任何配置中的 PDO entry 不受支持、无法注册或无法映射时，`configure()` 整体失败；不允许静默跳过。

### 6.4 可选扩展

在线发现和手动 AL 状态控制不放入必选操作表：

```c
struct mo_ecat_discovery_ops {
    int (*discover)(struct mo_ecat_backend *backend,
                    struct mo_ecat_discovery_result *result);
};

struct mo_ecat_manual_state_ops {
    int (*request_state)(struct mo_ecat_backend *backend,
                         int slave_index,
                         enum mo_ecat_al_state state);
};
```

可选操作表通过 `mo_ecat_backend` 中的对应指针挂载。后端初始化时必须验证：

```text
caps.online_discovery    == (discovery_ops != NULL)
caps.manual_state_control == (manual_state_ops != NULL)
```

核心层同时检查 capability 和操作表指针，仅在两者一致时暴露扩展 API。不允许后端用“返回成功但什么都不做”的方式伪装支持。

## 7. 主站生命周期与状态机

### 7.1 主站状态

```text
INIT
  │ 初始化完成
  ▼
IDLE
  │ configure 成功
  ▼
READY ◄────────────┐
  │ activate 成功   │ deactivate 成功
  ▼                 │
RUNNING ────────────┘
  │
  ├─ 短时 WKC/链路异常 → DEGRADED ──恢复正常──► RUNNING
  └─ 超过故障阈值       → FAULT

READY / RUNNING / DEGRADED / FAULT
  └─ close / destroy → IDLE → 释放对象

FAULT
  └─ reset / destroy 后重新 configure
```

- `INIT` 表示主站对象刚创建，内部状态机正在初始化。
- `IDLE` 表示主站空闲，未持有已配置的总线运行资源，可以执行 `configure()`。
- `READY` 表示后端已打开、映射已建立、过程数据区有效，可以执行 `activate()`。
- `RUNNING` 表示过程数据交换正常。
- `DEGRADED` 表示出现短时异常，但在策略允许范围内继续交换。
- `FAULT` 表示连续异常、链路丢失或安全条件触发。
- 第一版不允许 `FAULT → deactivate → activate` 的就地重启。`FAULT` 后必须 reset 或 destroy，再重新执行完整初始化流程，避免残留的 backend、PDO 映射或从站错误状态被继续使用。
- 短时可恢复异常由 `DEGRADED` 处理。如后续需要快速恢复，应新增显式 `RECOVERING` 状态和恢复次数上限，不复用 `deactivate()` 作为隐式恢复命令。
- 主站生命周期状态与从站 AL 状态是两个不同维度。

### 7.2 状态迁移规则

主站状态迁移必须集中在状态函数中完成。外部 API 不直接切换状态，只向主站对象提交命令，例如 `CONFIGURE`、`ACTIVATE`、`DEACTIVATE`、`RESET`。当前状态函数在 `USER_STATUS` 或自定义子阶段中检查命令和运行条件，合法时调用 `sm_transition()`，非法时拒绝命令。

允许迁移：

| 当前状态 | 目标状态 | 触发条件 |
|---|---|---|
| `INIT` | `IDLE` | `mo_ecat_master_dispatch()` 执行 INIT 状态，初始化条件满足 |
| `IDLE` | `READY` | IDLE 状态收到 `CONFIGURE` 命令，后端 open/configure 成功 |
| `IDLE` | `FAULT` | IDLE 状态执行配置失败且需要暴露故障 |
| `READY` | `RUNNING` | READY 状态收到 `ACTIVATE` 命令，后端 activate 成功 |
| `READY` | `IDLE` | READY 状态收到 `RESET` 命令并释放配置资源 |
| `RUNNING` | `DEGRADED` | 周期内出现短时 WKC、链路或后端异常 |
| `RUNNING` | `FAULT` | 周期内出现严重异常 |
| `RUNNING` | `READY` | RUNNING 状态收到 `DEACTIVATE` 命令，后端 deactivate 成功 |
| `DEGRADED` | `RUNNING` | 周期恢复正常 |
| `DEGRADED` | `FAULT` | 连续异常达到阈值 |
| `DEGRADED` | `READY` | DEGRADED 状态收到 `DEACTIVATE` 命令，后端 deactivate 成功 |
| `FAULT` | `IDLE` | FAULT 状态收到 `RESET` 命令并释放后端资源 |

除上述表格外的迁移均为非法迁移。非法迁移不调用 backend，不改变过程数据域，不改变 PDO generation。

### 7.3 状态机实现约束

- `statemachine_init()` 的初始状态函数为 `mo_ecat_master_state_init`。
- 主站状态函数集中放在 `src/mo_ecat_master_states.c`，声明放在 `src/mo_ecat_master_states.h`。
- 每个状态函数必须显式处理 `ENTER`、`USER_STATUS`、`EXIT` 三个阶段。
- `mo_ecat_master_state_init` 在 `ENTER` 阶段设置 `state = MO_ECAT_MASTER_STATE_INIT`。
- 创建完成后不会在 `create()` 内部隐藏调度状态机；应用必须调用 `mo_ecat_master_dispatch()`，INIT 状态在条件满足后自动迁移到 `IDLE`。
- `mo_ecat_master_state_ready/running/degraded/fault` 分别只在 `ENTER` 阶段写入对应状态 ID。
- 应用主循环或管理线程需要在固定位置每周期调用一次 `mo_ecat_master_dispatch()`，由它内部调用 `sm_dispatch()`，使当前状态的 `USER_STATUS` 分支被持续执行。
- `cycle_begin()` / `cycle_end()` 只负责 EtherCAT 过程数据收发和周期结果采集，不隐式调度主站状态机。
- API 函数只负责保存请求参数并提交命令；当前状态函数在自己的 `USER_STATUS` 或自定义子阶段判断命令是否合法，合法时完成资源准备、执行对应后端动作并调用 `sm_transition()` 发起迁移，非法时拒绝请求。
- 故障处理统一调用状态机迁移到 `FAULT`，不允许直接写状态字段。

### 7.4 过程数据域有效期

- `configure()` 创建或替换过程数据映像，成功后 `generation++`。
- `activate()` 开始周期交换，不改变 memory 指针和 generation。
- `deactivate()` 只停止周期交换，不释放映像，因此可以直接再次 `activate()`。
- 再次 `configure()` 或 `close()` 使旧映像和 PDO 指针失效。
- 运行期间不允许调用 `configure()`。

## 8. 实时周期

### 8.1 公共周期模型

```c
while (running) {
    struct mo_ecat_cycle_result result = {0};

    mo_ecat_master_dispatch(master);  /* 每周期固定调用一次状态机 */

    int begin_status = mo_ecat_master_cycle_begin(master, &result);

    /* 此时输入已更新 */
    read_inputs(master);
    run_controller();
    write_outputs(master);

    int end_status = mo_ecat_master_cycle_end(master, &result);

    if (begin_status < 0 || end_status < 0 ||
        result.diagnostics_required) {
        notify_management_thread();
    }
}
```

不在实时线程内直接调用可阻塞的 `read_diagnostics()`，而是通知管理线程处理。

### 8.2 周期结果字段写入规则

| 字段 | 写入阶段 | 规则 |
|---|---|---|
| 函数返回值 | begin / end | 分别表示两个阶段的执行结果 |
| `link_up` | begin | 接收后更新链路观测结果 |
| `actual_wkc` | begin | 接收过程数据后填写 |
| `expected_wkc` | configure / begin | configure 计算，begin 复制到周期结果 |
| `dc_time_ns` / `dc_time_valid` | begin | 接收后更新 |
| `backend_error` | begin / end | 仅记录本周期第一个错误，不覆盖 |
| `diagnostics_required` | begin / end | 任一阶段可从 0 置 1，不得清零 |

### 8.3 SOEM 映射

```text
activate     : 完成首次 send，为后续 receive 建立起点
cycle_begin  : ecx_receive_processdata
cycle_end    : ecx_send_processdata
diagnostics  : ecx_readstate + SOEM error ring
```

### 8.4 IGH 映射

```text
cycle_begin  : ecrt_master_receive
               ecrt_domain_process

cycle_end    : ecrt_domain_queue
               ecrt_master_send

diagnostics  : ecrt_master_state
               ecrt_domain_state
               ecrt_slave_config_state
```

`ecrt_slave_config_state()` 和 `ecrt_master_state()` 用于读取状态，不将它们解释为与 SOEM `ecx_writestate()` 等价的手动状态命令。

## 9. SOEM IOmap 安全策略

SOEM 的 `ecx_config_map_group(context, iomap, group)` 不接收缓冲区容量，并且在返回实际映射大小之前已经向 IOmap 写入数据。因此，“调用后再检查返回大小”不能保证内存安全。

本项目采用以下契约：

```c
struct mo_ecat_soem_options {
    size_t process_image_capacity;
};

int mo_ecat_soem_backend_init(
    struct mo_ecat_backend *backend,
    const struct mo_ecat_soem_options *options);
```

1. IOmap 容量是 SOEM backend 选项，不放入平台无关的 `mo_ecat_config`。
2. `mo_ecat_soem_options.process_image_capacity` 必须在初始化 SOEM backend 时明确给出，不使用隐式的固定 4096 字节数组。
3. SOEM backend 按该容量创建映射内存。
4. 为严格防止越界，项目需要为 SOEM 增加容量感知的 mapping 封装或维护一个小型补丁，使每次映射写入前检查剩余容量。
5. 如果容量不足，`configure()` 必须失败且不得进入 `READY`。

仅根据扫描阶段的 `Obits/Ibits` 推算大小可以作为预检，但不作为唯一安全保障，因为 PDO 配置回调可能在映射阶段改变实际布局。

## 10. 故障与诊断策略

周期快路径只记录固定开销的信息：

- 接口调用结果；
- 链路/domain 状态；
- 期望 WKC 与实际 WKC；
- DC 时间及有效性；
- 是否需要进一步诊断。

管理路径诊断内容包括：

- 从站 AL 基础状态、error 标志和 AL status code；
- 从站 online/operational 状态；
- 后端错误队列；
- 连续 WKC 异常次数；
- 故障恢复次数和最近恢复时间。

从 `RUNNING` 转入 `DEGRADED` 或 `FAULT` 的阈值不固化在 backend 中，而由核心层的平台无关故障策略配置决定。状态变化必须通过主站状态机完成。

## 12. 与现有代码的迁移计划

### 阶段 1：锁定契约

1. 新增配置、状态、周期结果和 backend 接口头文件。
2. 实现 SOEM backend 的最小可运行版本，验证生命周期、失败回滚、WKC 异常和 generation 失效。
3. 此阶段不改变现有对外 API。

### 阶段 2：迁移 SOEM

1. 将 `ecx_contextt` 从 `struct ec_master` 移入 `soem_backend_ctx`。
2. 将 `ecx_init()`、映射、收发和诊断调用移入 SOEM backend。
3. 实现有容量检查的 SOEM IOmap 映射。
4. 将现有 `ec_master_*` API 改为调用新核心层的兼容包装。

### 阶段 3：验证 IGH

1. 用最小 IGH backend 实现 `open/configure/activate/cycle_begin/cycle_end/deactivate/close`。
2. 确认核心层不需要因 IGH 的配置流程而修改。
3. 若差异只能通过 capability 或可选扩展表达，不将 IGH 私有概念加入核心对象。

## 13. 验收标准

- 核心层源码中不出现 `ecx_*`、`ecrt_*`、`ecx_contextt` 或 `ec_slave_config_t`。
- SOEM 与 IGH 都使用同一份 `mo_ecat_config` 完成配置。
- SOEM IOmap 容量只出现在 `mo_ecat_soem_options` 中，不泄漏到核心配置。
- PDO 引用数量、扁平化顺序和失败策略可由单元测试验证。
- capability 与可选操作表指针不一致时，backend 初始化失败。
- 实时周期内无动态内存分配、无阻塞状态等待、无直接日志输出。
- IGH 周期完整包含 `receive/process` 和 `queue/send`。
- SOEM IOmap 容量不足时安全失败，不产生越界写。
- `deactivate()` 后状态由 `RUNNING/DEGRADED` 迁移到 `READY`，可直接重新 `activate()`，且 PDO 引用仍有效。
- `FAULT` 只能通过 reset / destroy 释放资源后回到 `IDLE` 或重新创建，不允许就地重新激活。
- 重新 `configure()` 后旧 generation 的 PDO 引用被明确拒绝。
- 旧 `ec_master_*` API 在迁移期内保持源码兼容。
